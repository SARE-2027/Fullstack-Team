# Cart movement contract

## One report, one decision

The Pi collects scanner, camera and stable basket measurements locally and sends
one completed movement. The backend processes this movement once. A correct
movement updates the invoice atomically; an unidentified piece or weight mismatch
keeps the **whole movement** as NeedsConfirmation without adding/removing invoice units.
A scanner-only report needs no weight and bills immediately.

There are no partial reports, automatic correction movements, or automatic
reprocessing of earlier reports. Supervisor recovery uses ReconcileCartBasket.

## IDs and input

The server generates every CartMovementItem ID and SessionItem ID. The Pi does
not generate IDs per SKU/unit. Barcode identifies the catalog variant; it does
not identify a physical piece or invoice row.

The device retains message/operation identity (eventId, movementId), sequence and
boot ID for network retry safety. These are message metadata, not IDs of database
invoice units. The exact original message is retained across retries.

SignalR: `ReportCartMovement(sessionId, request)` at `/hubs/cart`.
HTTP: `POST /api/cart/{sessionId}/movements`, with the same request/result.
Both check that the device credential belongs to this session's cart. Admin JWTs
can manage; Staff JWTs can read individual sessions but cannot mutate them.

```javascript
const report = {
  eventId: crypto.randomUUID(), movementId: crypto.randomUUID(),
  sequence: currentSession.lastMovementSequence + 1, deviceBootId,
  startedAtUtc: startedAt.toISOString(), endedAtUtc: endedAt.toISOString(),
  isComplete: true, modelVersion: "products-v1",
  weight: { beforeG: 0, afterG: 50, isStable: true, toleranceG: 15 },
  items: [
    { action: 0, barcode: "A", source: 1 },
    { action: 1, barcode: "A", source: 0, confidence: 0.94,
      trackId: "42", cameraId: "basket" }
  ]
};
const result = await connection.invoke("ReportCartMovement", sessionId, report);
// One billed unit, two observations. Their IDs are generated by the server.
```

| Field | Meaning |
| --- | --- |
| eventId | Message UUID; reuse it and the exact contents on retry. |
| movementId | Operation UUID; a different eventId cannot reuse a stored movementId. |
| sequence | Next message counter within the session, starting at 1. Reconnect/reboot does not reset it. |
| deviceBootId | UUID of the device run; tracking IDs are scoped to boot/camera. |
| startedAtUtc / endedAtUtc | UTC interval, end >= start and at most one minute ahead of server time. Normalized to microseconds. |
| isComplete | Must be true; defaults to true. Partial reports fail validation before writes. |
| weight | Optional stable net basket weight before/after, grams. Required for Enter/Exit. A weight-only snapshot is supported. |
| weight.isStable | Must be true. Sensor stabilization belongs on the Pi. |
| weight.toleranceG | 0..100, default 15; cannot increase the server's configured tolerance. |
| items | Up to 100 observations, one per piece/action. No itemId input. Repeated identical SKUs are separate units. |
| modelVersion | Optional, max 50 characters, diagnostic model version. |

| Item field | Meaning |
| --- | --- |
| action | Scan=0, Enter=1, Exit=2, CancelScan=3. |
| barcode | Variant barcode, max 64 characters; may be null on an unknown physical observation. |
| source | Vision=0, Scanner=1. Model-to-barcode mapping remains Vision. Scan/CancelScan require Scanner. |
| confidence | 0..1; Vision needs the configured threshold. |
| sessionItemId | Existing invoice ID for Exit selection or CancelScan (required for cancellation). Scan and Enter reject this field. |
| trackId / cameraId | Optional, max 64 characters. Duplicate camera/track/action in one report is invalid. |

Enter automatically consumes the oldest active Scanner/Unconfirmed invoice unit
with the same barcode in this session. Earlier purchases are considered first,
then scans from this report in their input order. Each waiting unit can satisfy
only one entry. Once none remain, another Enter creates a newly billed unit.
Matching still requires the whole movement to pass identity/confidence and weight
checks; failure leaves waiting units and charges unchanged.

Scan and Enter carry no invoice-unit reference. CancelScan targets are excluded
from automatic placement within the same movement. For example, a later placement
needs only:

```javascript
await connection.invoke("ReportCartMovement", sessionId, {
  ...nextReportMetadata,
  weight: { beforeG: 0, afterG: 50, isStable: true },
  items: [{ action: 1, barcode: "A", source: 0, confidence: 0.95 }]
});
```

FIFO matching is an accounting rule for identical barcodes, not proof of physical
identity: a held scanned piece and another identical piece cannot be distinguished
by barcode and total weight alone. The held scan stays billed until explicitly
cancelled. Purchase price/weight snapshots are retained during placement.
Every Scan means a new purchase; there is no scanner-based identity-confirmation
command. Device orchestration must avoid sending a new Scan for a physical piece
that vision already added to the invoice.

## Validation and invoice rules

All observations are identified, planned and checked before any invoice mutation.
A mixed report with wrong weight does not bill even its valid scanner observations;
send a scanner-only report for an independent immediate scan.

Weight checks use known inside contents, continuity with the last accepted basket
weight, entering minus exiting unit weights and final expected contents. Held
scans remain billed but contribute no inside mass. Price/weight/barcode snapshots
are captured per invoice unit and survive catalog changes or deactivation.
Stored historical invoice rows may lack weight; this is checked where physical
weight is calculated, not assumed to be an incoming per-item weight.

Mixed exits/entries, several identical units and zero-net-weight product swaps
are supported. Same-track/camera/barcode Enter+Exit within a report has no invoice
effect. Exit uses an explicit reference, unique track, or financially equivalent
unit; different price/weight candidates need selection.

RemoveSessionItem marks intent only. CancelItemRemoval clears it. CancelScan
voids an unplaced scanned unit; a placed unit requires physical Exit. Neither a UI
click nor a retry can remove the same invoice charge twice.

Defaults: Vision confidence 0.80 and at most 15g tolerance, further capped by the
caller and one quarter of the smallest physical unit. Calibrate with real sensors.
Variable-weight pricing is separate work.

## Manual review and recovery

Statuses: Accepted, NeedsConfirmation, Cancelled. Every saved report is visible
through full SessionUpdated/session replies, with observation positions, server
IDs, outcomes and reasons. Uncertainty is not automatically a fraud accusation.

After an unresolved physical report, subsequent physical reports are retained
with MANUAL_REVIEW_REQUIRED, without invoice changes. Independent scanner-only
reports can still be accepted. Old reports are never retried/reapplied by a new
report. Resolve the actual basket state before continuing physical processing.

An Admin must physically check/restore the known contents, then invoke:

```javascript
await adminConnection.invoke("ReconcileCartBasket", sessionId, {
  eventId: crypto.randomUUID(), movementId: crypto.randomUUID(),
  sequence: currentSession.lastMovementSequence + 1, deviceBootId,
  stableBasketWeightG: checkedWeight,
  pendingMovementIds: currentSession.pendingMovements.map(x => x.movementId)
});
```

The exact current pending set and weight matching confirmed inside contents are
required. Recovery cancels unresolved reports; it does not silently approve their
items. If goods should be added after review, restore known state and report their
new scan/entry normally. Recovery preserves the accepted invoice and resets the
observed/accepted basket weight. Pending reports/removal intents block closure.
Held accepted scans alone do not block closure.

## Retry, storage and deployment

Receipt lookup precedes the open-session check: an exact retry can acknowledge
an operation after closure. Same eventId with changed contents/session is rejected.
Existing movementId with a new eventId returns MOVEMENT_ALREADY_RECORDED without
saving, consuming sequence or publishing again. Session concurrency and unique
receipt sequence protect concurrent requests. Movement, observations, invoice
changes, total and receipt save together; publication follows commit.

Join/HTTP snapshots recover missed events. Notifications remain best effort;
there is no durable outbox. Persist and serialize the Pi's delivery queue, register
SessionUpdated before connecting, and rejoin the cart after every reconnect.
Raw frame/load-cell samples stay on the Pi. If the device cannot stabilize, surface
the fault locally rather than invent a final reading.

Apply migrations through CleanUpCartMovementContract. They retain movement and
invoice rows, rename the old event table to cart_movement_items and backfill item
positions before adding the unique movement/position index. Supersede/Corrects
fields and scan indexes are removed. The required invoice barcode is backfilled
from its variant for historical rows before enforcing NOT NULL. Observations use
their parent movement's session; no duplicated session ID is stored per child.
Historical identity-confirmation effects become NoChange while their invoice
links remain intact. The runtime has no compatibility detection pipeline. The old
ProcessItemDetection method and /items HTTP route are absent.

```powershell
dotnet ef database update --project backend/SARE.Infrastructure --startup-project backend/SARE.Api
```

Shelf correlation, customer ownership/history and payments remain separate work.
The Pi still needs SKU training/mapping, physical direction/scan association,
stable measurements, retained delivery and a confirmation UI. Backend integration
tests do not measure model accuracy or sensor calibration.
